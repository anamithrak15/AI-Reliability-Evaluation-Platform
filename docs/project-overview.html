AI Reliability & Evaluation Platform

Run several language models over the same versioned dataset, score every answer, and compare them on quality, latency, tokens, estimated cost and failure rate, with regression detection and an explainable recommendation.

FastAPIPostgreSQLRedis + RQ React + TypeScriptLiteLLMRender + Vercel

1. Problem statement

Teams that build on large language models choose and change models with little evidence. A model is picked because a demo looked good, then a provider updates it, a prompt is edited or a cheaper model is swapped in, and nobody can say whether quality dropped.

Decisions by anecdote

Eyeballing a few answers does not show which model is better on the cases that matter, or by how much.

Silent regressions

Quality, latency or failure rate can slip after a model or prompt change, and nothing flags it.

Hidden trade-offs

The best model on quality may be slow or expensive. Quality, speed, cost and reliability must be weighed together.

Irreproducible tests

Ad-hoc prompts in a notebook cannot be re-run on identical inputs, so two comparisons are never truly comparable.

Cost surprises

Running many models over many cases against paid APIs can spend real money before anyone notices.

Misleading numbers

Failed calls counted as zero, or missing prices shown as free, make results look better or worse than they are.

2. Solution

The platform turns model selection into a repeatable experiment. A user imports a dataset of test cases, runs one or more models over it, and gets scored, comparable results. A baseline run turns every later run into a regression check.

CapabilityHow it works
Versioned datasetsJSON import; each version is immutable and has a SHA-256 content hash. Re-importing identical content is rejected, so a result always refers to exact inputs.
Asynchronous runsA case x model matrix runs on a worker with bounded concurrency, retries only for transient errors, per-model spend caps, cancellation and idempotent job delivery.
ScoringExact match, contains, regex, JSON Schema and classification evaluators. A case that cannot be scored gets null, never zero.
ComparisonSuccess and failure rate, quality, p50 and p95 latency (successful calls), tokens and estimated cost per model. Missing usage or price is shown as unavailable, never as 0.
Regression detectionCompares a run with a compatible baseline (same dataset content and evaluation profile) using configurable thresholds, sample-size guards and severities.
RecommendationHard constraints remove unsuitable models first; the rest are ranked by a documented weighted score. Every excluded model gets its reasons.
Case inspectionFor one case, shows the prompt, the expected answer and every model's output side by side.
AccountsEmail and password sign-in, private data per account, optional email verification, password reset, rate limits and quotas.
Demo mode. Deterministic mock models are always available, so the whole workflow runs without calling a paid provider. Live models are opt-in through LiteLLM.

4. High-level design

A single-page React app talks to a FastAPI service through one origin. The API is the only component that users reach. It stores everything in PostgreSQL, uses Redis for rate-limit counters and the job queue, and hands long-running evaluation to a worker. On free hosting the worker runs inside the API process.

Design decisions

DecisionReason
One origin through an edge proxyThe browser sees a single host, so session cookies stay first-party and no cross-origin (CORS) access is needed.
PostgreSQL as the source of truthRuns, results and summaries are relational and need transactions and compare-and-set state changes.
Redis for counters and the queueCheap shared state for rate limits and job delivery. The rate limiter fails open, so a Redis outage never takes the API down.
Worker separate from the APIEvaluations are slow and bursty. A separate worker keeps request latency stable.
Inline worker modeFree hosting offers no background workers, so the API process can run evaluations itself. Unfinished runs resume on start-up. This assumes one API instance.
LiteLLM behind one adapterOne call path for mock, local and hosted models, with timeouts, usage and price lookup in one place.
Immutable dataset versionsA result is only meaningful if the exact inputs can be identified later.

5. Low-level design

5.1 Backend layout

PackageResponsibility
app/apiHTTP routers: auth, datasets, runs, catalog, health. Thin: parse, authorise, delegate.
app/servicesBusiness logic: auth_service, dataset_service, run_service, comparison_service, queue, resume, run_state, mailer.
app/evaluationThe evaluation engine: orchestrator, evaluators, summary, regression, ranking, llm_adapter, mock_adapter, registry.
app/models, app/dbSQLAlchemy entities, sessions, seeding of the demo dataset.
app/schemasPydantic request and response models. Validation errors return 400 in a single envelope.
app/auth, app/corePassword hashing, tokens, session dependencies; configuration, rate limiting, client address, error envelope, logging.

Errors always use the shape {code, message, details?}. Validation errors are 400, missing or foreign resources 404, conflicts 409, rate limits and quotas 429.

5.2 Run lifecycle

Run creation, queuing and execution, from the user's click to the stored results.

  • Idempotency. The same Idempotency-Key returns the original run, scoped per account, so a retried request does not start a second run.
  • Claiming. The worker only starts a run it can atomically move from queued to running. A stale running run (no progress beyond a configured time) can be re-claimed after a crash.
  • Stopping. Between calls the worker checks for cancellation and the run deadline, so a cancel or timeout stops work cleanly.
  • Retries. Only transient failures (timeouts, provider errors) are retried, with backoff. Other failures are recorded as the case result.
  • Budget. A per-model USD cap applies to priced calls only; in-flight calls can exceed it slightly.

5.3 Run state machine

completed_with_errors means the run finished but some cases failed. Comparison and baselines are available for finished states; a baseline must be completed or completed_with_errors.

5.4 Evaluators

EvaluatorChecks
exact_matchOutput equals the expected value after configurable normalisation steps.
containsOutput contains a required string.
regexOutput matches a pattern.
json_schemaOutput parses as JSON and satisfies a schema.
classificationThe label field in the JSON output matches the expected label.

Each evaluator returns named metrics. A metric that cannot be computed is stored as null; summaries ignore nulls instead of counting them as zero.

5.5 Summaries, regressions and ranking

When a run finishes, one summary per model is stored: executed count, success and failure rate, quality, p50 and p95 latency over successful calls, tokens and estimated cost.

SettingDefaultMeaning
REGRESSION_QUALITY_DROP0.03Absolute quality drop that raises a finding
REGRESSION_FAILURE_RISE0.02Absolute failure-rate rise
REGRESSION_P95_RISE_PCT0.25Relative p95 latency rise
REGRESSION_COST_RISE_PCT0.20Relative cost rise
REGRESSION_MIN_SAMPLES5Below this many cases, no finding is raised

A baseline is only accepted if its dataset content and evaluation profile match the current run. Otherwise the request fails with a clear message and nothing is saved.

Recommendation. Ranking has two stages:

  1. Hard constraints. A model is excluded, with reasons, if it has too few executed cases (default minimum 5), quality below 0.5, a failure rate above 0.2, or breaches an optional p95 or cost-per-case limit.
  2. Weighted score. Remaining models are scored on quality (0.60), p95 latency (0.25) and cost per case (0.15). Latency and cost are min-max normalised across the compared models, so 1 is best. If a component is unavailable for a model, the weights are re-normalised over the components that exist, and the missing component is listed.

6. Data model

  • Immutability. Dataset versions and a run's config_snapshot never change, so a stored result can always be traced to exact inputs and settings.
  • Ownership. Datasets and runs carry a user_id. Every query filters by the signed-in user, and another account's resource returns 404.
  • Precision. Costs use fixed-point numerics; case inputs and configs are JSONB.
  • Migrations. Alembic manages schema changes: initial schema, run idempotency key, users and ownership, then email verification.

7. Security

ConcernHow it is handled
Passwordsargon2id hashes, minimum 10 characters, the same error for every login failure, hashes upgraded when parameters change.
SessionsSigned token in an HttpOnly, SameSite=Lax cookie (Secure in production). A per-user token_version revokes all sessions.
CSRFEvery state-changing /api call must carry X-Requested-With: fetch. Browsers cannot add it cross-origin without a denied CORS preflight.
Email linksVerification and reset use signed, single-purpose tokens. A reset token is bound to the current password hash, so it works once; it expires in 30 minutes and ends other sessions. "Forgot password" answers identically for unknown addresses.
Data isolationAll data is scoped to the account; foreign resources return 404 so existence is not revealed. Idempotency keys are scoped per account.
Abuse limitsPer-address rate limits (general, run creation, sign-in, sign-up), per-account email limits, dataset and active-run quotas, a global active-run cap, request size cap, no chunked uploads.
Client addressTRUSTED_PROXY_HOPS takes the address N entries from the right of X-Forwarded-For, so a caller cannot spoof it to evade limits.
Secrets and config.env is git-ignored. Production refuses to start with the development secret, insecure cookies, or required verification without a delivery method.
LogsStructured JSON with request IDs. Query strings and credentials are never logged; provider errors are redacted.
Browser headersContent-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy on the frontend.

8. Deployment

EnvironmentLayout
Local developmentDocker Compose: Postgres, Redis, API, worker and the frontend dev server.
Production-styleA second compose file with production images, nginx serving the built SPA and proxying /api, a separate worker, and no published database ports.
Free public hostingRender Blueprint (render.yaml) creates the API (Docker), PostgreSQL and Redis. Vercel serves the SPA and rewrites /api/* to Render. Email goes out through Brevo's HTTPS API.
Free-tier behaviour.
  • The API sleeps after 15 idle minutes; the first request then takes about a minute.
  • The free PostgreSQL database expires 30 days after creation.
  • Free Redis is in-memory, so rate-limit counters reset on restart.
  • No background workers, so evaluations run inside the API (RUN_WORKER_INLINE=true), and unfinished runs resume on start-up.
  • Outbound SMTP is blocked, which is why email uses an HTTPS API.

10. Benefits

Evidence over opinion

Every model is judged on the same inputs with the same evaluators, so differences are real and repeatable.

Catches regressions early

A baseline turns each run into a check, with severity and an explanation for every finding.

Balanced decisions

Quality, latency, cost and reliability are weighed in one documented formula, and exclusions come with reasons.

Honest numbers

Unscorable cases are null, missing prices are unavailable, and failed calls are not hidden. Nothing is silently counted as zero.

Cost control

Mock models by default, per-model spend caps, and run, case and concurrency limits keep experiments cheap.

Reproducible

Immutable dataset versions with content hashes and per-run config snapshots make any result traceable.

Private by design

Per-account data, safe sessions and abuse limits make it usable as a shared hosted service.

Runs anywhere

The same code runs locally in Docker, as a production-style stack, or on free public hosting.

11. Limitations

  • Mock models classify by keywords, so their results are meaningful only on the bundled demo dataset. They demonstrate the platform; they say nothing about real models.
  • Small samples give weak signals. Regression checks and the recommendation are skipped or flagged below a minimum sample size, but they are not statistical tests.
  • Rate limits are per client address and depend on a correct TRUSTED_PROXY_HOPS.
  • Inline-worker mode supports one API instance only.
  • Estimated cost is not an invoice, and some providers report no usage.
  • No roles or SSO. Email verification is optional and off by default.
  • Judge-model evaluation and scheduled runs are not built.
